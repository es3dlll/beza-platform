## 1. Executive Summary — الملخص التنفيذي

### 1.1 Vision — الرؤية
Beza Platform يهدف لأن يكون نظام التشغيل المالي الرقمي الوطني للجمهورية العربية السورية — منصة مفتوحة، آمنة، ومتوافقة مع المعايير المصرفية، تُمكن 22 مليون مقيم و 6 ملايين مغترب من إدارة أموالهم رقمياً بثقة.

### 1.2 Mission — الرسالة
بناء بنية تحتية مالية رقمية شاملة تجمع بين:
- **الشمول المالي:** وصول الخدمات المالية لكل سوري أينما كان
- **الامتثال التنظيمي:** الالتزام بمتطلبات المصرف المركزي السوري ومعايير AML/CFT
- **التقنية المفتوحة:** منصة قابلة للتوسع والتكامل مع النظام المصرفي الحالي
- **الأمان أولاً:** حماية بيانات وأموال المستخدمين كأولوية مطلقة

### 1.3 Elevator Pitch
"تطبيق واحد يدير فلوسك كلها — تحويلات، دفع فواتير، شحن رصيد، وتجارة إلكترونية — بدون ما تحتاج تحمل ١٠ تطبيقات."

### 1.4 Business Model Overview
| المصدر | الوصف | الهامش المتوقع |
|--------|-------|----------------|
| رسوم التحويلات | 0.5% - 1.5% من قيمة التحويل | 60-70% |
| رسوم الدفع | 0.3% - 0.8% من قيمة الدفع | 50-60% |
| رسوم الشحن | 1% - 2% من قيمة الشحن | 40-50% |
| خدمات التجار | اشتراك شهري + عمولة 0.5% | 70-80% |
| خدمات API | لكل طلب API | 80-90% |

**ملاحظة:** عند إطلاق منصة الصرافة (V2)، ستُضاف رسوم فارق سعر الصرف (0.5% - 2% فوق سعر السوق) كمصدر ربح رئيسي.

### 2.2 Competition Analysis — تحليل المنافسين

| المنافس | نقاط القوة | نقاط الضعف | حصتنا التنافسية |
|---------|-----------|------------|------------------|
| **Western Union** | علامة تجارية عالمية، شبكة واسعة، ثقة | رسوم عالية، لا يوجد تطبيق محلي، بطء في المعالجة | سعر أقل 50-70%، تحويل فوري |
| **MoneyGram** | حضور عالمي، شراكات محلية | رسوم عالية، تجربة مستخدم ضعيفة | دعم محلي، تكامل مع النظام المصرفي السوري |
| **الحوالات غير الرسمية (Hawala)** | مرونة، سرعة، ثقة مجتمعية | بدون رقابة، مخاطر أمنية، غير قانونية | شفافية، أمان، امتثال قانوني |
| **البنوك السورية الخاصة** | ترخيص رسمي، فروع محلية | تجربة رقمية ضعيفة، زحمة، بيروقراطية | تجربة مستخدم فائقة، سرعة، سهولة |
| **MTN Cash / Syriatel Cash** | انتشار واسع، قاعدة عملاء كبيرة | خدمات محدودة، واجهة مستخدم ضعيفة | منصة مالية شاملة، مرونة أكبر |

**التمايز الرئيسي لمنصة بيزا:**
- **الثقة:** أول منصة سورية مرخصة للخدمات المالية الرقمية الشاملة
- **الشفافية:** كل رسم وعمولة وسعر صفر معروض قبل أي عملية
- **السرعة:** تحويلات فورية على مدار الساعة
- **الشمول:** خدمات متكاملة (تحويلات، دفع فواتير، شحن، تسوق) في تطبيق واحد
- **المجتمع:** مصممة خصيصاً للواقع السوري واحتياجاته

### 3.4 Architecture Decision Records — سجل القرارات المعمارية

#### ADR-001: Modular Monolith on Laravel

| البعد | القرار |
|-------|--------|
| **السياق** | منصة مالية تحتاج فصل واضح بين الوحدات مع استقلالية تطوير كل وحدة |
| **القرار** | Modular Monolith — وحدات داخل Laravel، كل وحدة لها مجلداتها القياسية |
| **البديل المرفوض** | Microservices — تعقيد إضافي بدون حاجة في هذه المرحلة |
| **الأساس** | 14 مجلداً لكل وحدة (Actions, Controllers, Events, Listeners, Models, Services, ValueObjects, ...) |

#### ADR-002: Event-Driven Communication

| البعد | القرار |
|-------|--------|
| **السياق** | منع الاقتران المباشر بين الوحدات |
| **القرار** | التواصل حصراً عبر الأحداث — لا استدعاءات مباشرة للـ Services أو Models |
| **البديل المرفوض** | Facades, Helpers عابرة للوحدات |
| **الأساس** | `event(new EventName(...))` → Listener `ShouldQueue` → `handle(EventName $event)` |

#### ADR-003: ULID for Primary Keys

| البعد | القرار |
|-------|--------|
| **السياق** | جداول مالية تحتاج معرفات مرتبة زمنياً مع تفرد عالمي |
| **القرار** | ULID (26-char, Crockford Base32, k-sorted) |
| **البديل المرفوض** | UUID v4 (غير مرتب زمنياً), Auto-increment (قابل للتخمين والتصادم في التوزع) |

#### ADR-004: Money as Value Object (bigint)

| البعد | القرار |
|-------|--------|
| **السياق** | دقة العمليات المالية تتطلب عدم استخدام الفواصل العائمة |
| **القرار** | تخزين SYP بوحدة صغرى (فلس) في bigint، معالجة عبر كائن القيمة Money |
| **البديل المرفوض** | float, double, decimal (كلها تفقد الدقة) |

#### ADR-005: Append-Only Ledger (WORM)

| البعد | القرار |
|-------|--------|
| **السياق** | دفتر الأستاذ هو مصدر الحقيقة الوحيد للأرصدة — يجب ألا يُعدّل أو يُحذف |
| **القرار** | Append-only + Write Once Read Many — كل عملية مالية هي إضافة جديدة |
| **البديل المرفوض** | UPDATE/DELETE على السجلات المالية |
| **آلية الإلغاء** | إنشاء قيد عكسي جديد (reverse entry)، وليس تعديل/حذف القيد الأصلي |

| **تقلب سعر الصرف** | عالية | عالية | **حرج** | تحديث سعر الصرف كل دقيقة، تثبيت السعر وقت إنشاء المعاملة |

### 8.2 Mitigation Plans — خطط التخفيف التفصيلية

#### المخاطرة 1: انقطاع الكهرباء / الإنترنت
| الإجراء | الوصف |
|---------|-------|
| **Offline-First** | كل العمليات الحيوية يجب أن تعمل وضع غير متصل وتتزامن لاحقاً |
| **Local Caching** | تخزين البيانات الأساسية محلياً في الجهاز (الرصيد، آخر المعاملات) |
| **Auto-Resume** | استئناف المعاملات المقطوعة تلقائياً عند عودة الاتصال |
| **Retry Mechanism** | آلية إعادة محاولة ذكية مع exponential backoff |
| **Energy Efficient** | تصميم التطبيق ليكون خفيفاً على البطارية والبيانات |

#### المخاطرة 2: تقلب سعر الصرف
| الإجراء | الوصف |
|---------|-------|
| **Real-time Rates** | ربط بمزود بيانات موثوق لتحديث سعر الصرف كل دقيقة |
| **Rate Lock** | تثبيت سعر الصرف عند إنشاء المعاملة لمدة 5 دقائق |
| **User Visibility** | عرض سعر الصرف بوضوح قبل تأكيد المعاملة |
| **Hedging** | للتحويلات الكبيرة (>$1,000)، تطبيق تأكيد إضافي مع سعر محدد المدة |
| **History** | عرض سجل أسعار الصرف للمستخدم لبناء الثقة |

#### المخاطرة 3: عقوبات دولية / تعقيد تنظيمي
| الإجراء | الوصف |
|---------|-------|
| **Legal Counsel** | استشارة قانونية مستمرة متخصصة بالعقوبات والامتثال المالي |
| **Flexible Structure** | هيكلة الشركة والمنصة لتكون متوافقة مع القوانين المحلية والدولية |
| **Sandbox Approach** | البدء في بيئة آمنة وتوسيع الخدمات تدريجياً مع موافقة الجهات الرقابية |
| **Documentation** | توثيق كل قرار امتثالي مع مرجعية قانونية واضحة |
