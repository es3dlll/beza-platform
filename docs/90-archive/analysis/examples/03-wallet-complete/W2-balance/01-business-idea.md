# 01 - فكرة العمل وسيناريو المستخدم (Business Idea & User Scenario)

## الفكرة الأساسية

المستخدم يريد معرفة رصيده الحالي في كل moment. يحتاج عرض الرصيد ليكون:
1. **سريع** — استجابة < 50ms
2. **دقيق** — يعكس آخر حركة
3. **شامل** — عرض SYP + USD معاً
4. **غير مكلف** — تقليل ضغط DB عبر Cache

## سيناريو المستخدم (User Story)

```
بصفتي: مستخدم في Beza
أريد: عرض رصيدي الحالي لكل العملات
لكي: أعرف كم أملك قبل إجراء أي معاملة مالية
```

## قبول السيناريو (Acceptance Criteria)

| # | الشرط | الحالة |
|---|-------|--------|
| 1 | عرض رصيد محفظة SYP | إجباري |
| 2 | عرض رصيد محفظة USD | إجباري |
| 3 | عرض الرصيد المجمد (frozen) | إجباري |
| 4 | عرض رقم المحفظة (wallet_number) | إجباري |
| 5 | تحديث الرصيد فور إجراء أي معاملة | Realtime |
| 6 | Cache 30 ثانية لتقليل ضغط DB | Performance |
| 7 | إبطال Cache تلقائياً بعد أي معاملة | Consistency |
| 8 | عرض الرصيد حتى لو كان 0 | UX |
| 9 | خطأ إذا لم توجد محفظة (نادر) | Exception |
| 10 | استجابة < 50ms للأحمال العادية | Performance |

## لماذا Cache 30 ثانية؟

1. **تخفيف ضغط DB**: كل مستخدم يفتح التطبيق → طلب رصيد
2. **سرعة الاستجابة**: Redis أسرع 100× من MySQL
3. **مؤقت مناسب**: المستخدم لا يتوقع تحديث الرصيد كل millisecond
4. **إبطال تلقائي**: عند إجراء أي معاملة (تحويل، صرافة)، يُمسح Cache

## تدفق الشاشات (User Flow)

```
[فتح التطبيق] → [الرئيسية] → [طلب الرصيد] → [عرض SYP + USD]
                      ↑                              ↓
                [إعادة توجيه بعد معاملة]      [تحديث تلقائي]
```
