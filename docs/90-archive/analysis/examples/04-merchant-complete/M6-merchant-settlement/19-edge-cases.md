# 19 - حالات الحافة (Edge Cases) للتسوية البنكية

## نظرة عامة
هذا المستند يغطي جميع السيناريوهات النادرة وغير المتوقعة التي قد تحدث أثناء عملية التسوية البنكية، مع الحلول المعتمدة والمعالجة البرمجية لكل حالة.

## 1. الحساب البنكي مغلق أو منتهي الصلاحية

```
السيناريو: التاجر لديه حساب بنكي مسجل، لكن البنك أغلقه أو انتهت صلاحية IBAN
           دون أن يقوم التاجر بتحديث بياناته في المنصة.

الإجراء:
1. تفشل محاولة التحويل البنكي من API البنك (رمز خطأ: ACCOUNT_CLOSED)
2. إعادة الرصيد المجمد إلى محفظة التاجر فوراً
3. إرسال إشعار عاجل للتاجر (FCM + SMS + Email)
4. تعطيل الحساب البنكي تلقائياً وجعله غير نشط
5. طلب من التاجر إضافة حساب بنكي جديد قبل إعادة المحاولة
6. إشعار فريق الدعم للتواصل مع التاجر

الرسالة للتاجر: "❌ الحساب البنكي غير نشط. يرجى تحديث بيانات حسابك البنكي وإعادة المحاولة."
```

```php
// معالجة حساب بنكي مغلق
if ($bankResponse['error_code'] === 'ACCOUNT_CLOSED' || $bankResponse['error_code'] === 'IBAN_EXPIRED') {
    // تعطيل الحساب البنكي
    MerchantBankAccount::where('iban', $settlement->iban)
        ->update(['is_active' => false]);

    // إشعار عاجل للتاجر
    $merchant->notify(new BankAccountExpiredNotification($settlement));
}
```

## 2. فشل التحويل البنكي المتكرر (Bank Transfer Repeated Failure)

```
السيناريو: فشلت محاولات التحويل البنكي 3 مرات لأسباب مختلفة
           (مرة: خطأ في الشبكة، مرة: مهلة البنك، مرة: خطأ داخلي).

الإجراء:
1. المحاولة 1: إعادة بعد ساعة ← فشل
2. المحاولة 2: إعادة بعد 24 ساعة ← فشل
3. المحاولة 3: إعادة بعد 3 أيام ← فشل
4. إيقاف المحاولات وإبلاغ فريق الدعم البشري
5. تحويل الحالة إلى failed مع سبب "تحتاج تدقيق يدوي"
6. إعادة الرصيد كاملاً إلى المحفظة
```

```php
// بعد 3 محاولات فاشلة
$settlement->update([
    'status'         => 'failed',
    'failure_reason' => 'فشل التحويل البنكي بعد 3 محاولات - تحتاج تدخل يدوي',
]);
```

## 3. نزاع التاجر على حساب التسوية (Merchant Disputes Settlement)

```
السيناريو: التاجر يدعي أن المبلغ المحتسب للتسوية أقل من المتوقع
           (مثلاً: المبيعات 5000 USD لكن التسوية 4500 USD).

الإجراء:
1. إيقاف التسوية الحالية وتحويلها إلى status: dispute
2. فتح تذكرة دعم تلقائية
3. إرسال تقرير تفصيلي للتاجر يوضح:
   - إجمالي المبيعات
   - العمولات والرسوم
   - المرتجعات والتصريفات
   - رابط لكل معاملة مسرودة
4. فريق الدعم يراجع النزاع يدوياً
5. إذا ثبت خطأ الحساب → إعادة حساب التسوية
6. إذا الحساب صحيح → شرح للتاجر وإغلاق النزاع

مدة معالجة النزاع: 3-5 أيام عمل.
```

```php
// إنشاء نزاع تسوية
$settlement->update(['status' => 'dispute']);
DisputeTicket::create([
    'merchant_id'    => $merchant->id,
    'settlement_id'  => $settlement->id,
    'reason'         => $merchant->input('dispute_reason'),
    'status'         => 'open',
]);
```

## 4. تسوية جزئية (Partial Settlement - الحد الأدنى لم يتحقق)

```
السيناريو: تاجر لديه 40 USD فقط في محفظته (أقل من الحد الأدنى 50 USD).

الإجراء:
1. لا يتم إنشاء طلب تسوية (يُرفض)
2. يبقى الرصيد متراكماً للدورة القادمة
3. إشعار التاجر: "الرصيد الحالي غير كافٍ للتسوية (الحد الأدنى: 50 USD)"
4. خيار: يمكن للتاجر إضافة رصيد لاستكمال الحد الأدنى

معالجة برمجية: في التسوية التلقائية، يتم تخطي التجار الذين
               لا يستوفون الحد الأدنى تلقائياً.
```

```php
// في خدمة التسوية التلقائية - تخطي التجار الذين لا يستوفون الحد
Merchant::chunk(100, function ($merchants) use ($minAmount) {
    foreach ($merchants as $merchant) {
        $balance = $merchant->wallet('USD')->balance;
        if ($balance < $minAmount) {
            continue; // تخطي لهذه الدورة
        }
        // معالجة التسوية...
    }
});
```

## 5. تحويل العملة (Currency Conversion at Settlement)

```
السيناريو: تاجر يعمل بـ SYP لكن حسابه البنكي بالدولار USD.

الإجراء:
1. حساب رصيد SYP في المحفظة
2. تحويل SYP → USD بسعر صرف اليوم (من API مصرف سورية المركزي)
3. خصم رسم تحويل العملة 0.5% إضافية
4. تحويل المبلغ بالدولار للحساب البنكي
5. إرسال إشعار يوضح سعر الصرف المستخدم
```

```php
// تحويل العملة في وقت التسوية
$rate = CurrencyConverterService::getRate('SYP', 'USD');
$usdAmount = round($sypAmount / $rate, 2);
$conversionFee = round($usdAmount * 0.005, 2); // 0.5%
$netUsdAmount = $usdAmount - $conversionFee;
```

## 6. تأخير بسبب عطلة البنك (Holiday Delay)

```
السيناريو: طلب تسوية في يوم الجمعة (عطلة البنوك في سوريا)
           أو في عطلة رسمية.

الإجراء:
1. إنشاء طلب التسوية بحالة pending
2. تجميد الرصيد في المحفظة
3. جدولة التنفيذ لأول يوم عمل بعد العطلة
4. إشعار التاجر بأن التحويل سيتم في أول يوم عمل

قائمة العطل الرسمية:
- الجمعة والسبت (عطلة أسبوعية)
- العطل الرسمية (عيد الفطر، عيد الأضحى، رأس السنة، إلخ)
```

```php
// التحقق من أن اليوم هو يوم عمل
public function isBankingDay(Carbon $date): bool
{
    // الجمعة والسبت عطلة
    if ($date->isFriday() || $date->isSaturday()) {
        return false;
    }

    // العطل الرسمية (قابلة للتوسع)
    $holidays = [
        '01-01', // رأس السنة
        '08-03', // عيد الثورة
        '17-04', // عيد الجلاء
        '06-05', // عيد الشهداء
        // إضافة العطل الإسلامية (حسب التقويم)
    ];

    return !in_array($date->format('m-d'), $holidays);
}
```

| # | الحالة | النتيجة | رمز الرد |
|---|--------|---------|----------|
| 1 | رصيد < 50 USD | رفض (422) + إشعار التاجر | MINIMUM_SETTLEMENT_NOT_MET |
| 2 | تسوية معلقة سابقة | رفض (422) + "لديك طلب معلق" | PENDING_SETTLEMENT_EXISTS |
| 3 | تحويل بنكي فاشل | إعادة رصيد + إعادة محاولة (3 مرات) | BANK_TRANSFER_FAILED |
| 4 | رسوم Beza 2% + تحويل 1% | خصم تلقائي (3% إجمالاً) | - |
| 5 | حساب بنكي خاطئ | failed + تدقيق يدوي | INVALID_BANK_ACCOUNT |
| 6 | نزاع التاجر على الحساب | dispute + تذكرة دعم | - |
| 7 | تحويل عملة (SYP→USD) | تحويل بسعر الصرف + رسم إضافي | - |
| 8 | عطلة بنكية | pending حتى أول يوم عمل | - |
