# 14 - معاملات قاعدة البيانات (Database Transactions — ACID)

## لا حاجة لمعاملات قاعدة البيانات

عملية التنصيب **لا تستخدم DB::transaction** لأن كل خطوة هي عملية مستقلة بذاتها:

| الخطوة | هل تحتاج transaction؟ | لماذا؟ |
|--------|----------------------|--------|
| فحص المتطلبات | لا | فحص محلي — لا يمس قاعدة البيانات |
| إعداد قاعدة البيانات | لا | مجرد اختبار اتصال + إنشاء DB |
| إعداد البيئة (.env) | لا | كتابة ملف — لا يمس قاعدة البيانات |
| تشغيل الترحيلات | لا | كل ميجريشن مستقل (Laravel يديرها) |
| إنشاء المشرف | لا | عملية INSERT واحدة بسيطة |
| تعطيل المثبت | لا | كتابة قيمة في .env |

## لماذا لا حاجة لـ ACID هنا؟

**Atomicity (الذرية)**: كل خطوة إما تنجح أو تفشل بشكل مستقل.
- فشل الخطوة 4 (ميجريشن) لا يعني التراجع عن الخطوة 3 (.env)
- المستخدم يمكنه إعادة محاولة الخطوة الفاشلة فقط

**Consistency (الاتساق)**: النظام يبقى متسقاً لأن:
- `.env` مكتوب قبل الترحيلات (إذا فشلت الترحيلات، المستخدم يحذف `.env` ويعيد)
- الترحيلات Laravel تضمن اتساق قاعدة البيانات
- إنشاء المشرف عملية بسيطة

**Isolation (العزل)**: لا توجد عمليات متزامنة — المستخدم وحيد أثناء التنصيب.

**Durability (الديمومة)**: كل خطوة تكتب مباشرة:
- `.env` يُكتب على القرص (`file_put_contents`)
- الترحيلات تُلزم في MySQL (`COMMIT` تلقائي)
- المشرف يُدرج في قاعدة البيانات

## متى قد نحتاج transaction؟

في الخطوة 5 (إنشاء المشرف)، لو كان هناك عمليات متعددة (إنشاء مشرف + محفظة + إعدادات)، كنا سنحتاج `DB::transaction`. لكن المثبت يبقيها بسيطة:

```php
// إنشاء المشرف فقط — لا معاملات مطلوبة
$user = User::create([
    'name'     => $request->input('name'),
    'email'    => $request->input('email'),
    'phone'    => $request->input('phone'),
    'password' => Hash::make($request->input('password')),
    'is_admin' => true,
]);
```

## مقارنة مع A1-register

| الخاصية | A1-register | SY1-install |
|---------|-------------|-------------|
| يستخدم DB::transaction | ✅ نعم (إنشاء مستخدم + محفظتين) | ❌ لا |
| عدد العمليات في المعاملة | 3 (user + 2 wallets) | 1 (admin user فقط) |
| سبب المعاملة | ضمان إنشاء المحافظ مع المستخدم | غير مطلوب — عملية واحدة |
| التراجع عند الفشل | ROLLBACK تلقائي | إعادة المحاولة يدوي |

## تدفق الفشل والتعافي

```
◉ المستخدم في الخطوة 4 (ترحيلات)
  ↓
  ┌─ فشل الميجريشن (خطأ في SQL) ──────────────────────┐
  │                                                     │
  │  الحالة: .env مكتوب ✓                               │
  │          قاعدة البيانات فارغة                       │
  │                                                     │
  │  الإجراء:                                           │
  │  1. المستخدم يراجع الخطأ (مثلاً: إضافة مفقودة)     │
  │  2. يعيد تشغيل الخطوة 4                             │
  │  3. الميجريشن يعمل كأنه أول مرة                     │
  │  4. إذا استمر الفشل:                                │
  │     - المستخدم يحذف .env يدوياً                      │
  │     - يعيد التنصيب من البداية                       │
  └─────────────────────────────────────────────────────┘

◉ المستخدم في الخطوة 5 (إنشاء المشرف)
  ↓
  ┌─ فشل إنشاء المشرف ─────────────────────────────────┐
  │                                                     │
  │  الحالة: الترحيلات تمت ✓                            │
  │          الجداول موجودة ✓                           │
  │          المشرف لم يُنشأ                            │
  │                                                     │
  │  الإجراء:                                           │
  │  1. المستخدم يعيد إدخال بيانات المشرف              │
  │  2. يعيد تشغيل الخطوة 5                             │
  │  3. لا حاجة لإعادة الترحيلات                        │
  └─────────────────────────────────────────────────────┘
```

## ملاحظة أمان

لأن المثبت لا يستخدم `DB::transaction`، ويتم تنفيذ Artisan commands مثل `migrate --force`، فهناك احتمال أن تنجح بعض الخطوات وتفشل أخرى. لكن هذا مقبول لأن:

1. البيئة غير مستقرة بعد — المستخدم هو من يدير العملية
2. كل خطوة قابلة لإعادة التشغيل
3. `.env` يحتوي على `INSTALLER_LOCKED` فقط عند نجاح كل شيء
4. السجل (Log) يحفظ كل خطوة بشكل منفصل
