# الميثاق المعماري الشامل - منصة بيزا (Beza Platform)
## دليل إعادة البناء الكامل، الهيكلية، العمليات، والرؤية الاستراتيجية

### 1. الرؤية الاستراتيجية والسياق المؤسسي

منصة بيزا هي البنية التحتية المالية الرقمية الوطنية المصممة خصيصًا للجمهورية العربية السورية. تهدف إلى تمكين 22 مليون مقيم و6 ملايين مغترب من الوصول إلى خدمات مالية رقمية آمنة، شفافة، ومتوافقة تنظيميًا. ينبني المشروع على تحويل بيئة مالية لا يزال النقد يهيمن عليها بنسبة تتجاوز التسعين بالمئة، إلى نظام تشغيل مالي موحد يعيد الثقة إلى المعاملات اليومية، ويقلل التكاليف، ويدعم الشمول المالي.

ترتكز الهوية المؤسسية على مبادئ غير قابلة للمساومة:
- **الثقة قبل السرعة** في كل تصميم تقني أو تجربة مستخدم.
- **الشفافية المالية المطلقة**: كل رسم، كل عمولة، وكل سعر صرف معروض بوضوح قبل التأكيد.
- **الامتثال الصارم**: تصميم يلبي متطلبات المصرف المركزي السوري (CBS) ومعايير مكافحة غسل الأموال وتمويل الإرهاب (AML/CFT) منذ السطر الأول.
- **الأولوية العربية**: واجهات، توثيق، ومصطلحات مصممة بالعربية أولاً مع دعم كامل لاتجاه النص من اليمين لليسار.
- **الأمان المدمج**: حماية البيانات والأرصدة ليست طبقة إضافية، بل جزء من نواة النظام.

### 2. الفكرة الأساسية ونموذج الحل

**المشكلة الجوهرية** التي تعالجها المنصة تتمثل في تشتت القنوات المالية، ارتفاع كلفة التحويلات المحلية والدولية، انعدام الشفافية في تتبع الأرصدة، وصعوبة دمج الوكلاء والتجار الصغار في النظام الرسمي، بالإضافة إلى تعقيد الامتثال للجهات الرقابية.

**الحل المقدم** هو نظام تشغيل مالي متكامل يعتمد على معمارية الكتلة النمطية الموحدة (Modular Monolith). يربط النظام المحافظ الرقمية، شبكة الوكلاء المعتمدين، التجار، المغتربين، والجهات الحكومية عبر واجهات برمجية قياسية وآمنة. النواة الصلبة للمنصة هي دفتر الأستاذ المالي (Ledger) الذي يعمل بنظام القيد المزدوج، والمدعوم بمحرك تسوية مركزي يضمن دقة الأرصدة بنسبة مئة بالمئة، مع توليد تقارير رقابية يومية موقعة رقميًا ومرسلة تلقائيًا لواجهة المصرف المركزي.

### 3. الفلسفة المعمارية والقواعد غير القابلة للتفاوض

لإعادة بناء النظام أو توسيعه، يجب الالتزام بهذه العقود المعمارية بشكل صارم:

| القاعدة | الوصف |
|---------|-------|
| **G-01: Modular Monolith فقط** | يمنع تحويل الوحدات إلى خدمات مجهرية قبل الإصدار السادس وموافقة لجنة الهندسة |
| **G-02: Event Bus للتواصل الداخلي** | يمنع استدعاء خدمات أو نماذج وحدات أخرى بشكل مباشر. كل تفاعل يمر عبر مسار الإرسال، الاستماع، والمعالجة |
| **G-03: دفتر الأستاذ هو مصدر الحقيقة الوحيد** | Append-Only, WORM. يمنع الحذف أو التحديث المباشر. عمليات الإلغاء تتم عبر إنشاء قيود عكسية جديدة |
| **G-04: CFE يملك الأرصدة حصريًا** | لا يجوز لأي وحدة أخرى كتابة أو تعديل الأرصدة مباشرة |
| **G-05: ULID + bigint + Money** | ULID لكل الجداول الأساسية. النقود كقيمة صحيحة كبيرة (bigint) بوحداتها الصغرى. يمنع استخدام الأنواع العائمة |
| **G-06: Zero Trust** | توكنات قصيرة العمر، ربط الأجهزة، تشفير AES-256 و TLS 1.3 |
| **G-07: الفئات نهائية + strict_types** | كل ملف PHP: `declare(strict_types=1)` و `final class` |
| **G-08: اختبار لكل نقطة نهاية** | Feature tests لكل API endpoint |
| **G-09: توثيق متزامن مع الكود** | OpenAPI, ADRs, CHANGELOG محدّث مع كل تغيير |
| **G-10: لا منطق تجاري في المتحكمات** | Controllers رقيقة، Services تحتوي المنطق، Models للبيانات فقط |

### 4. الهيكلية الكاملة للمشروع

ينقسم المستودع إلى أربعة محاور رئيسية:

#### الواجهة الخلفية
`backend/` — Laravel 11، وحدات داخل `app/Modules/`. كل وحدة تحتوي على متحكمات، خدمات، نماذج، أحداث، مستمعات، هجرات، اختبارات، ومسارات API.

#### واجهات المستخدم
- `frontend/admin/` — React + TypeScript (لوحة تحكم)
- `frontend/mobile/` — Flutter (Super App)

#### التوثيق والهندسة
- `docs/architecture/` — قرارات وميثاق
- `docs/financial-core/` — محركات ودفتر أستاذ
- `docs/features/` — مواصفات الوحدات
- `docs/journeys/` — رحلات المستخدم
- `docs/operations/` — تشغيل ونشر وإصدارات
- `docs/planning/` — خرائط طريق ومتطلبات

`README.md`، `LICENSE`، `.gitignore` — راجع `docs/operations/releases/` لسجل التغييرات وأدلة النشر

### 6. العمليات الأساسية وتدفق البيانات

#### دورة المعاملة المالية

```
مستخدم/نظام ← مصادقة ← صلاحيات ← فحص احتيال ← CFE ← Ledger ← حدث ← إشعارات ← تسوية
```

1. يبدأ المستخدم أو النظام بطلب عملية
2. تمر الطلب بطبقة المصادقة والتحقق من الصلاحيات
3. يُفحص الطلب ضد قواعد كشف الاحتيال في الوقت الفعلي
4. يُرسل الطلب إلى CFE الذي ينفذ الخصم/الإيداع ضمن معاملة DB معزولة
5. يُسجل القيد في دفتر الأستاذ (Append-Only)
6. يُطلق حدث نجاح أو فشل
7. تستمع الوحدات (إشعارات، تسوية، تحليلات) وتنفذ مهامها

#### دورة التسوية والامتثال

```
جدولة تلقائية ← مقارنة الأرصدة ← كشف الفروقات ← تصنيف ← تقارير CBS ← توقيع ← إرسال ← أرشفة
```

#### إدارة الهوية والحدود

```
مستوى T1 (أساسي) ← T2 (موثق) ← T3 (كامل) — كل مستوى يفتح حدودًا أعلى
```

### 7. الامتثال، الأمان، والمراقبة التشغيلية

- تقارير مطابقة لمتطلبات CBS
- حفظ السجلات ≥ 5 سنوات
- توقيع رقمي (SHA256WithRSA) لكل تقرير
- تشفير AES-256 للبيانات المخزنة
- TLS 1.3 للنقل
- Prometheus metrics + 5-dimensional health check
- Slack + PagerDuty للتنبيهات

### 8. سير العمل الهندسي وضمان الجودة

- **Git Flow:** main للنتاج، develop للتطوير، feature للمهام، hotfix للطوارئ

- **CI:** فحص تنسيق، تحليل سكوني، اختبارات، OpenAPI drift check

### 9. دليل إعادة البناء الكامل (خارطة التنفيذ)
